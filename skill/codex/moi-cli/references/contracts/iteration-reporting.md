# 每次迭代的横向、纵向与对比报告

每次 Skill 版本迭代都必须同时交付三份主报告和一份机器可读清单，不能只发布 ZIP、文档或若干命令回执。

## 必备交付物

在当次独立证据目录中提供：

- `横向纵向功能报告.md`：横向覆盖全部 24 个产品入口，纵向说明 Workflow、Catalog、Knowledge 的新增能力、原有能力和未验证边界。
- `原版与dev版功能对比报告.md`：对照原版稳定 CLI / Skill、当前 dev CLI / Skill、命令与合同差异、实际新增能力和剩余缺口。
- `总体进展报告.md`：本版目标、实际变化、真实验收、发布检查、保留对象、风险与下一步。
- `report-manifest.json`：版本、CLI 版本与源码 commit、环境、三份报告文件、场景计数、限制和证据链接。

## 结论口径

- 横向功能报告先列“应该覆盖的功能点”和“当前做到哪一层”；对比报告先列“原版记录、当前 dev 结果、差距、验收结论”，不要把大量原始观察计数放在功能说明之前。
- 对比表按 24 个入口逐行呈现。使用百分比时写成 `通过数/固定场景数（百分比）`，同时保留部分完成和失败数；没有新增 dev 验收的入口明确写“未新增验收”，不能留空让读者猜。
- 纵向对比优先使用本轮固定场景集合；原版与 dev 条件或分母不同，不做百分比相减或总体平均。
- 命令兼容性、业务场景验收和文档覆盖分开报告，不把 24 个菜单有文档写成全部功能通过。
- 数量只针对明确的场景和条件；不得把命令数、文件数、API 数或历史证据数换算成产品覆盖率。
- 百分比只能用于有确定边界的集合，例如“原 Skill 使用的 133 个命令中 133 个通过 dev help”。使用百分比时必须同时写出分子、分母和集合含义。
- 原版与 dev 的历史记录按 regular/candidate 分开，不用 stable regular 的历史成功证明 dev 当前通过。
- 每个失败或部分完成项都要写出实际影响；不能用其它路径成功掩盖原命令失败。
- 新版本只记录本次已证实的变化；未运行的新场景标记 unverified，不因版本升级自动视为通过。

## 迭代验收

正式构建安装前准备上述交付物，并从包根目录执行：

```sh
MOI_ITERATION_EVIDENCE_DIR='<本次证据目录>' bash scripts/validate.sh
```

校验会检查三份主报告、24 个菜单、manifest 版本、场景状态、限制和证据链接。缺少任一必需内容即失败。
若只修改文档而未执行新线上场景，也必须写明未新增线上验收，不能用旧回执冒充本版新证据。

报告使用自然中文：先讲现在能做什么、比原版多什么、哪些仍未通过，再给证据和技术 ID。
