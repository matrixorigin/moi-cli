# 失败恢复合同

先按错误发生位置分类：CLI 参数/schema、认证/权限、网络/工具、服务受理、异步运行、业务
结果或产物核验。不要把所有失败归因于环境。

- 命令拒绝或 schema 失败：修正结构或缺少输入，不能重发未经修正的请求。
- 认证或权限失败：保留服务端错误，停止绕过；不要切换身份、角色或低层 API。
- 超时、连接断开或未知状态：查询原对象详情；确认未接受前不得重复写入。
- 异步失败：保存 task/execution/job ID、状态和错误，只有对应领域文档和用户授权允许时才重试/恢复。
- 结果为空：先判断空结果是否是合法业务结果，再报告查询范围和 limit；不要用重跑制造数据。
- 下载或产物失败：保留原任务/文件 ID，核验服务端状态；不要重复上传或创建第二个任务作为替代。

每次恢复都要说明：原操作、已知 ID、服务端状态、可恢复动作、执行的恢复动作以及仍待核验的结果。

多步任务在每次继续前可运行 `task_blueprint.py recover --run-dir DIR` 做只读判断。只有返回
`ready_for_single_execution` 时才考虑一次新的主调用；`blocked_unknown_submission` 只能查原对象，
`acceptance_incomplete` 只能补原回执的验收，`acceptance_failed` 需要另建明确授权的恢复步骤。
恢复检查不会执行 CLI，也不会把修改目录、改 invocation ID 或改验收预期当作重试依据。

覆盖或验收报告还要分清下面四种情况：

- 缺信息：没有已指定的接收方、测试成员、外部目标或安全连接；说明缺什么，不断言产品做不到。
- CLI缺输入：服务确实需要某字段，而当前help/schema/正式调用合同没有可传入口；记录字段和证据。开放object本身不够证明缺输入，还要查对应领域的现有调用者。
- 输入错误：配置、引用类型、命名空间或候选归属不对；先按正式发现结果修正。保留原失败与复测，不把它算产品故障。
- 正确输入仍失败：保留同一目标、实际响应、任务及读回状态；取得日志或明确合同后才认定根因，不把500或模型自述当诊断。

删除等操作返回错误也可能已发生部分变更。分别回读控制关系和实际可读数据；列表消失不证明访问已撤销。
SQL空结果本应是合法结果；异步query-result及下载有500记录，不能静默转为空数组。另有正式sql run内联零行成功的限定证据，见[SQL路径选择](../recipes/run-sql-and-fetch-result.md#合法零行查询的内联路径)；新查询不是原statement的结果恢复，不能无说明重执行或推广所有500都表示零行。
