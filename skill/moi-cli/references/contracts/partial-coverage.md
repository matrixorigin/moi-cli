# 部分通过的补测与收口

“部分通过”不是一个可以长期挂着的总状态。它必须拆成能分别判定的子项，并说明下一项
到底能补测、缺什么条件，还是根本不属于 CLI 的证明范围。

## 先固定验收粒度

1. 从功能清单逐项取出业务动作、输入变体、异常分支和结果断言，不以命令名代替功能点。
2. 通用功能只验通用合同；具体数据源、模型、文件格式若已有独立功能点，不要求在通用条目里
   再穷举一次。反过来，功能点明确写出的变体不能用“主路径成功”省略。
3. 页面颜色、卡片、按钮、复制交互和实时徽标属于 UI 验收。CLI 可以证明对应数据和动作，
   但不能把数据存在写成页面表现通过。
4. 分别记录“整个功能点通过”和“CLI 可承担部分已覆盖”。混合功能点仍有 UI 残留时，
   不能为了提高数字把前者改绿。

## 每个剩余项都必须有关闭方式

为每个剩余子项保存以下信息：

| 字段 | 要求 |
| --- | --- |
| `assertion` | 还要证明的具体行为，不写“其它未覆盖” |
| `class` | `cli_testable`、`missing_condition`、`cli_gap`、`product_defect`、`ui_only` 之一 |
| `evidence` | 已有回执、help/schema、缺失对象或缺陷证据 |
| `next_action` | 下一条正式 CLI 路径，或需要准备/修复的具体条件 |

`cli_testable` 必须先查正式 help、schema 和发现入口，再执行最小补测。不能用没跑过代替
CLI 不支持。`cli_gap` 必须指出缺哪个输入或输出；`missing_condition` 必须写出成员、连接、
设备、预算或后台对象的具体名称和用途。`product_defect` 需要正确输入、实际响应及读回结果，
不能把输入错误或模型自述当缺陷。`ui_only` 转交页面验收，不反复跑 CLI。

## 不把下列情况当成完整通过

- 命令存在、schema 通过、开放 JSON 字段被接受；
- 列表能读但搜索、排序、分页或目标状态未核对；
- 本地下载成功但外部目标端没有收到文件；
- 当前用户能配置权限但被授权成员的实际允许/拒绝未验；
- 用客户端后处理冒充服务端筛选或页面交互；
- 用另一条替代路径成功掩盖原路径失败。

补测后保留原“部分通过”记录，再追加新证据和状态变化。只有全部该功能点要求的子项都有
结论，才把该项称为验收完整；仍未通过的子项按上表保留，不用平均覆盖率掩盖。
