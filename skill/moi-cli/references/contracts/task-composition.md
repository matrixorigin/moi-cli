# 业务目标编排合同

复杂任务先明确用户要验收的结果，再选择能力和 CLI。能力目录是当前基线的归并结果，
不是固定数量的产品真理。静态检查通过也不能证明所有业务能力已在线可用。

开始前按[能力边界](capability-boundary.md#执行前范围判断)逐步判定范围，向操作者说明
尚未覆盖、已知失败或缺条件的步骤；已有补测授权时按其边界继续，不能以部分可用承诺整个目标。

复杂任务使用[本地任务记录与接续](../recipes/record-and-resume-task.md)落盘，不只保存在对话里。
步骤发送前持久占用；依赖核验后才可向下游执行；未知结果不得重发。
`resume` 仅检查本地证据，不调用产品、不添加授权，已核验步骤冻结。

## 目标拆解

```yaml
goal: 用户最终可以观察到的结果
scope: {workspace_id: 已确认, environment: 当前 CLI endpoint}
acceptance: [内容、数量、引用、目标可见性等用户关心的断言]
steps:
  - capability_id: 从目录选择已有业务能力；未验证场景保持 unverified
    inputs: [已发现的对象引用、用户选定的数据、参数]
    outputs: [服务端返回的引用及所属类型]
    depends_on: [真正需要的上游步骤]
    verify: 对目标结果的断言和查询方式
    resume: 原对象的状态查询方式
```

`task_run.py` 拒绝未知 capability ID。新场景挂到已有业务目标并保留未验证边界；
确需独立能力时先维护唯一目录，不能为继续执行伪造 ID。

仅加载依赖能力的 domain/Recipe。步骤间连接带类型引用：`workspace + object_type + id`，
需要时附带 version；字段同名不代表 ID 可互换。数值型 Catalog ID 和 UUID 不能自行转换出关联。

## 完成与恢复

- 分别记录输入配置、本次执行和本次输出。Workflow 已发布、历史执行完成，不能证明本次新输入已处理；
  Knowledge 已存在不能证明新增文档可检索。
- 上游输出满足下游输入合同才继续。解析产物、Catalog file、Knowledge source 是不同对象；source job
  完成之后还需索引与引用核验，才能用于带引用的 Agent 问答。
- 保留服务端状态。SQL 的 `success` 与 Workflow 的 `completed` 分别触发本域核验，不把未知枚举映射为成功。
  资源启用、执行状态、产物就绪和访问权限分开记录。
- 部分成功按文件/source/node 保存范围；先核实恢复语义。若正式retry会整次新跑，则先评估已成功步骤的重放风险，
  不能把它描述为只重试失败节点，不重建全部资源。
  失联保持 unknown，先查原执行；没有幂等合同就不自动重发。
- `reconcile_required`、权限变化或版本冲突不是自动运行 reconcile/repair 的授权。
- 撤销是新的有影响动作，不能把删除资源、取消运行或撤回发布当作通用自动回滚。

## 证据预算

- 默认投影 ID、状态、数量、分页和结果结构。Workflow 参数、trace、结果字符串可能含凭证或渠道地址，
  在本机投影后才展示，不整包写入聊天或报告。
- 返回条数和 total 分别报告；需要穷尽时才按 CLI 支持的分页读取后续页。
- `{}` 记录为“exit 0、没有可判定列表字段”。可能是空列表省略、缺少输入或输出合同；没有 response 合同
  或独立证据时，不断言没有资源，也不直接判为产品故障。
- 支持形态与验证范围分开：`static`、`discovery_verified`、`read_closed_loop_verified`、
  `write_closed_loop_verified`。列表成功不代表写入闭环通过，历史结果检查不代表本次执行通过。

## 能力归并

比较业务目标、主对象、生命周期、输入输出和完成证据。只增加 endpoint、菜单入口或节点实现时复用已有
capability；出现独立用户目标或不同完成合同时才拆分。WorkItem 在明确目标下也可形成独立功能，例如解析
并交付文件；不因它是节点就排除，也不因节点多就机械扩张目录。
